# Бизнес-требования

## Участники и права

Владелец (owner): компания, сотрудники, каталог, интеграции, агент, заявки, расходы. Администратор (admin): операционная настройка без передачи владения и изменения подписки. Оператор (operator): диалоги, ответы, заявки и их статусы; каталог только чтение. Аналитик (viewer): агрегаты и каталог, без переписок и персональных данных. Покупатель: только собственный диалог и заявки в своём канале. Системный worker: ограниченные операции для конкретного tenant/job. Поддержка платформы не получает автоматический доступ к перепискам.

В MVP UI сотрудников и приглашений отложен, используется только owner; проверки полномочий и модель memberships создаются сразу.

## Правила предметной области

Цена и остаток принадлежат варианту, а не общему товару. Каждый товар имеет хотя бы один вариант: для простого товара создаётся default-вариант в той же транзакции. Один склад на организацию в MVP. Цена в копейках, RUB, без float. Характеристики модели и варианта хранятся отдельно; неизвестное значение не заполняется догадкой. Для электроники различать память, цвет, состояние, гарантию и комплектацию.

Заявка `requested` — намерение покупателя, не оплата и не гарантия наличия. Она не уменьшает остаток. Сотрудник подтверждает её в `confirmed`, выполняя резерв. `completed` списывает резерв; `cancelled` освобождает его. Для MVP нет автоматического истечения резервов: сотрудник отвечает за отмену. Состояния и транзакции описаны в DATABASE_DESIGN.

Наличие считается достоверным только после сверки магазина. Предложенный срок свежести — 24 часа, настраивается владельцем в допустимых границах. Если данные старше срока, агент не обещает наличие. Даже свежий остаток не гарантирует физическое наличие при продажах вне платформы: владелец проверяет заявку.

Диалог после handoff находится под управлением сотрудника до явного возврата агенту. ИИ не отправляет параллельные ответы. Покупатель может запросить человека в любое время. За пределами рабочего времени — честное сообщение о времени ожидания, без обещания немедленного ответа.

## Нефункциональные требования

До пилота: tenant-тесты обязательны; восстановление backup проверено; ошибки не раскрывают секреты; отсутствуют отрицательные доступные остатки; каждый webhook сохраняется до успешного ACK. Предварительные эксплуатационные цели: ACK webhook p95 <1 с, ответ на обычный вопрос p95 <15 с при доступном LLM, окно выполнения AI ≤30 с. Это бюджеты проектирования; замерить на нагрузке пилота, не считать SLA. Продолжительный сбой LLM переводит обращения человеку.

Исходные допущения для нагрузочного теста: 5 магазинов, 5 000 вариантов на магазин, 10 входящих сообщений/с суммарно короткими всплесками. Подтвердить по пилоту. Поведение при лимите: сохранить обращение, поставить статус ожидания/передачи, не терять сообщение.
