## CODE COMPLETE

### Модель и поиск

Маршруты ниже находятся под `/api/v1/organizations/{id}`.

Миграция `00028_real_estate_delegation.sql` расширяет `platform.property_listings` типизированными колонками. Жизненный цикл объекта хранится отдельно от проверяемой доступности. Дополнительные характеристики включают санузлы, этажность, год постройки, ремонт, меблировку, лифт и парковку. Цена хранится в минимальных единицах указанной валюты, без конвертации. Старые записи сохраняют исходные значения. Новые атрибуты неизвестны до появления данных источника.

`POST /operations/properties/discover` принимает типизированные критерии, включая город, район, тип сделки, характеристики и границы площади. Для ценового интервала и сортировки по цене обязательна валюта. Запрос возвращает до 20 записей, номер страницы и `has_more`. PostgreSQL применяет детерминированный порядок с UUID в качестве последнего поля сортировки. По умолчанию возвращаются активные объекты с действующим подтверждением доступности. Явный фильтр по статусу позволяет сотруднику видеть исторические записи с фактической доступностью. Действующий `/operations/properties/search` сохраняет прежний формат и сравнивает цены в RUB.

### Customer, Sales и Business Manager

`POST /agent-delegations/real-estate` запускает существующую очередь через профиль `agency/real_estate`. Customer сохраняет переданные подтверждённые параметры. При недостающих обязательных полях сохраняются их ключи и текст уточнения. Следующий запрос с `previous_task_id` дополняет сохранённый контекст того же диалога. Произвольный текст пожеланий сохраняется как контекст для сотрудника и сам по себе не создаёт фильтров.

Sales выполняет типизированный поиск и вторично читает подходящие объекты перед предложением. Изменившиеся цены сверяются с бюджетом, а недоступные объекты исключаются. Сводка сравнивает доступные варианты по цене, локации, площади и комнатам. Структурированный результат содержит ID, тип, точные значения и известные характеристики. Business Manager агрегирует завершённые дочерние задачи и возвращает до трёх проверенных вариантов. Полные снимки шагов остаются в дочерних execution records, а в родительском результате карточки не дублируются. Agent Registry, Orchestrator, SQL Queue, worker, lease, correlation ID, повторные попытки и аудит используются по действующей модели делегирования. В команде семь агентов. Analytics сохраняет действующие возможности.

### Просмотр и Human Approval

`POST /agent-delegations/property-viewing` принимает выбранный объект, ID предложения того же диалога, интервал из существующего календаря и комментарий. Customer проверяет принадлежность к предложению. Sales перепроверяет объект и связанное предложение расписания. `POST /agent-delegations/property-viewing/{task}/prepare` регистрирует заявку из сохранённого результата под ключом родительской задачи и повторно валидирует объект и время. Внешний канал сохраняет фактического клиента из диалога. `GET /operations/property-viewings/{id}` возвращает типизированную проекцию заявки, назначенных специалистов календаря, решение и версию.

Сотрудник использует действующие действия Order API `confirm`, `reject`, `cancel` и `complete` с правом обработки заявок, версией и ключом идемпотентности. Просмотр использует календарь. Статус объекта при записи на просмотр сохраняется. Действительное решение и событие аудита фиксируются в одной транзакции. После записи события SQL Queue сохраняет дочернюю задачу Business Manager с исходным correlation ID. Задача формирует ответ из актуальной версии, а устаревшее событие получает `superseded`.

Рабочий вход — авторизованный оператор с подтверждёнными структурированными параметрами. Обработчик свободного текста в Telegram, WhatsApp и Instagram сохраняет существующее поведение и сам не инициирует Real Estate делегирование. Операция подготовки заявки вызывается отдельно после сохранения предложения просмотра. Родитель просмотра завершает подготовку и последующие решения обрабатываются как связанные с ним задачи.

### Доставка и изоляция

Результаты поиска, уточнения и решения по просмотру проходят через существующие очереди. Перед mock-доставкой проверяются tenant, привязка получателя, согласие на обновления, разрешения канала, доступность объекта и версия заявки. При изменении существенных данных ранее поставленное предложение блокируется. Instagram использует отдельный offline build tag и SQL fixture для изолированной базы `aba_test`. Обычный worker сохраняет отключённый Instagram send. Telegram и WhatsApp используют режим `mock`. Реальные интеграции, deployment и рабочие данные исключены из прогона.

Источники property и заявки используют существующие политики FORCE RLS и составные tenant FK. Проекции worker требуют точного lease, ожидаемого агента и сохранённых результатов допустимого предыдущего шага. Сотрудники видят только заявки и аудит организации, к которой у них есть доступ.
