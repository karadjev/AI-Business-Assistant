# Единый выпуск коммуникаций и подписок

## Публикация

1. Сверить действующий manifest, шесть контейнеров, PostgreSQL и активный Compose override. Сверить единый manifest, образы, архив исходников и доказательства.
2. Для точного manifest получить подписанную независимую D2 либо фактическое отдельное Owner Risk Acceptance согласно правилам проекта. Рецензент проверяет образы, транзакции миграций, FORCE RLS, webhook, запрет внешних отправок, права администратора и восстановление. Аттестация связывает manifest и образы. Артефакты для рецензента не содержат production-секретов и клиентских данных.
3. Подтвердить свежий backup и сверку отпечатков восстановления. Остановить API и worker на переключение. Мигратор из проверенного образа 37 должен оставить схему 37 и 70 таблиц FORCE RLS. Финальный мигратор должен оставить схему 38 и 74 таблицы FORCE RLS. Все операции Compose используют действующий override. Промежуточное приложение во время миграций не запускается.
4. Поднять API, worker и web. Подтвердить 6/6 healthy. Создать отдельного синтетического владельца, организацию с выделенным UUID и обязательный review Inbox. Выдать разрешение на изменение тарифа только синтетическому владельцу. Действующий пилот автосервиса сохраняется.
5. Проверить публичный Inbox через короткую тестовую сессию. Проверить mock Telegram, черновик, Human Approval, mock delivery, приглашение, изменение тарифа, исчерпание лимита, CSRF и отказ соседнему арендатору. Завершить тестовые сессии. Рабочий webhook и внешние отправки остаются выключены.
6. При инциденте остановить автoобработку Inbox выбранной организации и при необходимости отключить её канал. Обязательное согласование сохраняется. Приостановить подписку для блокировки новых задач и подключений. После исправления разрешать новые операции отдельно. Не возобновлять старые черновики и неопределённые доставки автоматически.
7. До новых данных допустим последовательный откат пустых 38 и 37 с проверкой отпечатков и возвратом исходных образов. При появлении новых данных сохранить схему 38 и поднять проверенный recovery с интерфейсом схемы 37. Не удалять и не заменять действующий том. Восстановление из архива проводить сначала в отдельном томе.

## Telegram Bot API

1. Владелец создаёт выделенного бота и передаёт токен через закрытое серверное секрет-хранилище. Сервер проверяет принадлежность через getMe. Подготовить выделенный HTTPS webhook и отдельный secret_token. Исключить путь с токеном из логов.
2. После отдельного допуска зарегистрировать webhook. Проверить getWebhookInfo, авторизованное входящее событие, отклонение неправильного секрета и единственную обработку повтора.
3. Отключение включает закрытие ingress, удаление webhook и при необходимости отзыв токена у BotFather. Внешние отправки требуют отдельного разрешения. [Telegram Bot API](https://core.telegram.org/bots/api#setwebhook)

## WhatsApp Business Cloud API

1. Владелец выделяет Meta app, WABA и Phone Number ID. Подготавливает системный токен с минимальными правами, App Secret и verify token. Секреты устанавливаются отдельным защищённым серверным процессом.
2. После допуска сверить принадлежность номера и WABA, HTTPS challenge, X-Hub-Signature-256 и подписку. Проверить обработку разрешённого события, отказ для чужого номера, дедупликацию и ограничения окна.
3. Для исходящих нужны отдельный GO, подтверждённые шаблоны и финансовый допуск. Для отключения снять локальный допуск и отозвать ненужный токен Meta. [Meta WhatsApp Cloud API](https://developers.facebook.com/documentation/business-messaging/whatsapp/get-started)

## Instagram

1. Владелец выделяет профессиональный аккаунт и Meta app с Instagram Login. Задаёт точные HTTPS OAuth redirect и webhook URL, App Secret и разрешения instagram_business_basic и instagram_business_manage_messages.
2. После допуска пройти OAuth с одноразовым state. Проверить привязку account ID, challenge, подпись, допустимое сообщение, отказ для чужого аккаунта, срок и отзыв токена. Хранить App Secret и токены зашифрованно.
3. Внешние отправки отключены. При отключении остановить обработку webhook, отозвать разрешения и проверить отказ старому токену. [Meta Instagram Login](https://developers.facebook.com/documentation/instagram-platform/instagram-api-with-instagram-login)

## Внешний S3 backup

1. Владелец создаёт приватный bucket и префикс, определяет регион и срок хранения. Роль VPS получает PUT/GET только на этот префикс. Удаление выполняется Lifecycle по согласованному правилу. Сохранять минимум две проверенные точки восстановления. [Amazon S3 Lifecycle](https://docs.aws.amazon.com/AmazonS3/latest/userguide/intro-lifecycle-rules.html)
2. Владелец назначает хранителя ключа. На VPS установить публичный PEM и сверенный SHA-256 сертификата, одобренные AWS CLI и OpenSSL. В защищённый systemd EnvironmentFile добавить ABA_OFFSITE_BUCKET, ABA_OFFSITE_PREFIX, AWS_REGION, ABA_OFFSITE_CERTIFICATE и ABA_OFFSITE_CERT_SHA256. Приватный ключ хранитель оставляет офлайн.
3. Подключить настройки к существующему расписанию. Установить TimeoutStartSec=50min. Проверить совпадение активного Compose override, checksum локального архива и readback зашифрованной копии.
4. Офлайн скачать ciphertext, сверить оба SHA-256 через offsite_restore.py и восстановить архив в отдельном пустом томе. Сверить таблицы, FORCE RLS и отпечатки. Указать дату проверки восстановления. До её успешного завершения внешняя копия остаётся BLOCKED.
