# Retention capability: operator workflow 10В

Только локальный/offline workflow; документ не разрешает изменение рабочих секретов или перезапуск рабочего стека.

## Согласование и выполнение

1. Определить конкретные tenant и окно обслуживания. Не выводить ключи, proof или hash в терминал/отчёт. Остановить планирование очистки штатно в управляемом окружении; не завершать чужие процессы принудительно.
2. API и worker должны использовать одинаковый retention key. Отдельный `CATALOG_RETENTION_KEY` (32 bytes в hex), если задан, отделяет ротацию очистки от `AUTH_EMAIL_KEY`. Без него сохраняется прежнее domain-separated derivation от email key. Не менять email key ради очистки: он также шифрует email outbox. Пустой/отсутствующий optional key сохраняет совместимость; malformed непустой key блокирует старт.
3. После согласованной доставки ключа в оба процесса развернуть/перезапустить их только отдельным разрешённым действием. Mixed old/new API недопустим: прежний upload/save также привязывает свою capability. Секреты не вводятся в UI или HTTP.
4. Войти владельцем нужного магазина, открыть «Центр управления каталогом → Правила и хранение», обновить данные. Поставить явное согласие и нажать «Перепривязать очистку». Альтернатива — существующий authenticated/CSRF-protected BFF POST `/api/v1/organizations/{id}/catalog-control/retention-binding` с `expected_version` и `confirm:true`. Proof в запросе отсутствует.
5. Backend проверяет owner, tenant RLS, serializes tenant writes, блокирует policy и проверяет версию. Привязка, повышение версии и append-only audit выполняются одной транзакцией. Сроки, hold и каталог не меняются. Staff/outsider запрещены; устаревшее/повторное подтверждение возвращает409. После неясного исхода обновить страницу и проверить версию/audit, не повторять POST вслепую.
6. Проверить на синтетическом held/expired job, что новый worker имеет scope только выбранного tenant, старый proof больше не перечисляет этот tenant через catalog policy, hold сохранён, audit присутствует. Прежняя совместимость с telegram worker proof остаётся отдельным существующим разрешением; её нельзя считать отозванной этой операцией.
7. Повторить явно для каждого согласованного tenant. Нет глобального rebinding и GET не перепривязывает. Для tenant без policy допустима expected_version0. До перепривязки новый worker пропускает tenant. Worker, уже начавший транзакцию до смены binding, может завершить разрешённую минимизацию: для строгой границы сначала дождаться штатного завершения старых задач.

## Ошибка и откат

При ошибке транзакция не оставляет частичной перепривязки. Version conflict требует refresh и нового ручного подтверждения. При несовпадении ключей API/worker очистка не выполняется новым worker; не ослаблять RLS. Возврат к прежнему ключу требует отдельного operator решения, согласованной конфигурации обоих процессов и owner rebinding; глобальный SQL UPDATE недопустим. Переход на standalone retention key не изменяет email ciphertext, provider keys или channel capabilities.

Никакой реальный ключ или рабочий tenant не ротировался в этапе10В. Проверки используют только synthetic keys в изолированной БД.
