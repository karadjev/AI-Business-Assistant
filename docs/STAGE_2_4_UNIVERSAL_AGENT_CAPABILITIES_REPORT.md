# Stage 2.4 — Universal Business Intelligence & Agent Capabilities

## Baseline

До начала изменений прочитаны отчёт Stage 2.3, его журнал проверок, десять документов Universal Business Architecture и roadmap. Проверены PostgreSQL migrations, shared queue, существующий Orchestrator, registry, tools, семь определений агентов, аудит и approvals. [Матрица исходного состояния](../.local/stage-2-4/BASELINE.md).

Stage 2.3 подтвердил семь ограниченных сценариев на PostgreSQL, восстановление worker, approvals, аудит и каналы. Stage 2.4 продолжает те же registry, worker и хранилища. Предыдущие отчёты и evidence сохранены.

## Universal Business Context и Industry Profiles

Migration 00019 добавляет модель, отрасль и версию профиля в существующую строку организации. Старый тип бизнеса сохранён для обратной совместимости. Изменение профиля требует полномочий владельца тестового tenant и ожидаемой версии. В worker профиль читается с проверкой SQL lease. Контекст агента получает модель, отрасль, версию и часовой пояс. Backend вычисляет доступные операции. Стартовый список профилей расширяется согласованным изменением Go и SQL. Профили продуктовой торговли отклоняются.

Dashboard отображает действующий профиль. PATCH `/api/v1/organizations/{id}/agent-business-profile` даёт основу для будущего мастера onboarding. API возвращает 409 при попытке записи поверх более новой версии. Полноценный мастер, источники услуг, клиентов, локаций, правил ценообразования и истории пока не интегрированы в новый контекст.

## Product Operations

Для durable задач доступны цена, карточка и остаток указанного варианта. Действия снова используют текущий Runner и Tool Registry. RLS проверяет tenant, связанный диалог, владельца и конкретный вариант. Карточка содержит данные существующего каталога. Проверка остатков использует действующий механизм freshness и возвращает unknown, если источник устарел. Количество для нового durable действия фиксировано на одной единице. Существующий поиск товара остаётся в прежнем channel pipeline. Durable поиск по категории, typed attributes, сравнение и проверка совместимости остаются открытыми.

## Service Operations и Universal Orders

Сервисные профили не получают доступ к товарным операциям. Существующие сервисные validators и order backbone сохраняются. Service catalog, доступность ресурсов, защита от двойной записи и сохранение сервисных, ремонтных, custom и hybrid заказов требуют отдельной реализации и проверки. Подтверждение legacy product orders сотрудником сохранено. Расчёт строительных материалов и выпуск коммерческого предложения через агента не подключены.

| Marketing | Действующий внутренний черновик по approval | Сегменты, контент-план и оценка эффективности |

Периоды относятся к дате создания заказов, которые сейчас завершены. Сумма заказов отличается от сверенной выручки. Средний чек округляется вниз до копейки. Отсутствие заказов в периоде даёт нулевое количество; средний чек в таком случае не выводится. Сценарий Analytics → Marketing → Business Manager использует результаты из PostgreSQL и учитывает отказ владельца. Расширенные сценарии A–E целиком остаются открытыми.

## Frontend и Real API E2E

В раздел AI settings добавлены профиль, семь специалистов, детали возможностей и разрешений, команды для доступных операций, задачи, результаты, аудит и текущий раздел approvals. Управление доступно владельцу. UI использует действующий BFF, сессии и CSRF.

Chromium проверил свежий standalone Next.js через настоящий Go API, Go worker и disposable PostgreSQL. Первый browser run подтвердил одобрение и перезапуск worker, но assertion прочитал тело ответа HTTP 204 в сценарии отклонения. После исправления все три сценария прошли. В них проверены вход, профиль, семь агентов, роли, CSRF и tenant isolation, создание задачи, статус, результат, аудит, одобрение, отклонение и завершение задачи после перезапуска worker. Сценарий команды, отклонения и аудита выполнен при viewport 390×844. Исходная попытка и trace сохранены. Стенд использует внутреннюю Docker-сеть и синтетические учётные записи. Проверки артефакта и исходников прошли до и после прогона.

## Миграция и изменённые файлы

- `apps/api/migrations/00019_business_agent_context.sql` и проверка версии в `internal/platform/db/db.go`. Схемы до 00019 не редактировались.
- `apps/api/internal/agentruntime/{profile,service,worker}.go`, `apps/api/internal/http/agents.go`, `apps/api/internal/agent/tools.go`, `apps/api/internal/catalog/service.go` и `apps/api/internal/specialists/specialists.go`.
- `apps/api/tests/integration/{business_context_stage24_test,database_test,instagram_schema_stage22_test}.go` и существующий синтетический browser fixture.
- `apps/web/src/components/{AgentTeam,AISettings,AgentApprovals}.tsx`, `apps/web/src/app/premium.css`, `apps/web/src/app/api/[...path]/route.ts` и `apps/web/tests/agent-team-real-api.spec.ts`.
- Этот отчёт, матрица и журналы в `.local/stage-2-4/`.

Первый SQL прогон выявил несовместимость rollback guard. Down новой миграции пропускал откат, когда уже имелась история агентов Stage 2.3. 00019 теперь наследует отказ для накопленной истории, а также защищает изменённые отраслевые профили. Исходный FAIL сохранён.

Следующий SQL прогон обнаружил, что `aba_app` имеет право менять только разрешённые колонки `organizations`. Вместо выдачи новых UPDATE privileges использована узкая функция с фиксированным `search_path`, проверкой `agent_owner`, CAS по ревизии и ограничением пары отрасль–модель в БД. Повторный прогон подтвердил девять профилей, запрет чужого доступа и конфликт ревизии.

Существующий сценарий чтения малого каталога с двумя соседними каталогами по 6 001 варианту дважды завершился `SERVICE_UNAVAILABLE`. PostgreSQL зафиксировал истечение односекундного SQL deadline. Для этой транзакции применено существующее решение из `ControlPage`, `SET LOCAL jit=off`. Оно оставляет прежний deadline, RLS, SQL-выборку и настройки pooled connections. Исходное падение и повторная проверка хранятся отдельно.

После изменения оба чтения малого tenant с принудительным generic plan прошли за 151 и 84 мс. В полном прогоне PostgreSQL тесты миграции, RLS, durable queue и recovery, а также регрессии Telegram, WhatsApp и Instagram завершились с exit 0.

## Security Testing

PostgreSQL подтвердил `FORCE RLS` и негативные SELECT/INSERT/UPDATE/DELETE для 51 таблицы. Новая матрица отдельно проверяет отказ чтения и записи профиля другого tenant, запрет неподдерживаемого отраслевого профиля, отказ на устаревшей ревизии и терминальный отказ без результата при попытке открыть чужой вариант. Действующий integration suite проверяет конкуренцию worker, восстановление истёкшего lease, повтор задачи, approval и аудит. Входные данные нового профиля ограничены серверным набором пар. Нет новых инструментов внешней отправки или записи товарных остатков.

Расширенная проверка prompt injection для сценариев A–E, нагрузочные rate-limit тесты новых агентных инструментов, конкуренция бронирований и целостность новых типов заказов остаются NOT RUN. Провайдеры и внешние операции оставались отключены. Тестовые стенды использовали синтетические данные.

## Следующие приоритеты

Нужны версионированные профили атрибутов и отраслевые поисковые поля с данными о совместимости, затем отдельные service resources, доступность и атомарная запись. После этого можно включить preparation tools для новых типов заявок, сохранив существующие согласие и подтверждение сотрудником. Обязательные проверки производства и live-провайдеров остаются вне текущей приёмки.
