# Stage 2.3 — Multi-Agent Runtime & Business Operations

**Ограниченный runtime семи агентов подтверждён на изолированной PostgreSQL.** Полный отраслевой функционал остаётся за рамками пройденных проверок.

## Исходное состояние

Stage 2.2 подтвердил migration 00017, 47 FORCE RLS таблиц, три tenants, общую SQL-очередь, восстановление worker и регрессию Telegram, WhatsApp и Instagram. Проверены код семи специалистов, Agent Registry, Orchestrator, типизированные инструменты, permissions, бизнес-модель и AI settings. Git всё ещё без первого commit. Исходный Git status и evidence предыдущих этапов сохранены.

## Durable Task Storage

Migration 00018 добавляет tenant-scoped задачи, execution records, approvals и аудит. Задание хранится отдельно от записи доставки. API сохраняет задачу и её запись в существующей `channel_inbox` в одной транзакции. Задача, ожидающая подтверждения, получает запись доставки в транзакции решения владельца. Совпадающий ключ идемпотентности возвращает прежний ID, изменённый запрос даёт конфликт. Сохранены инициатор, агент, действие, ссылка на variant или диалог, parent/correlation, deadlines, приоритет по умолчанию и состояние. Runtime допускает владельцев тестовых организаций.

## Execution Records и worker

Worker использует собственный lease в том же SQL inbox. Claim использует `FOR UPDATE SKIP LOCKED`, определяет полномочия инициатора и создаёт запись попытки. Успех фиксирует результат, исполнение, бизнес-статус, approval и подтверждение очереди в одной транзакции. Просроченный lease закрывает старую попытку состоянием interrupted. Старый worker теряет право записать результат. Допустимы три попытки с backoff, ограничением времени и терминальным состоянием. Одна задача выполняется одним worker за раз, один worker обрабатывает агентные задачи последовательно. Agent timeout до пяти секунд, максимум один вызов инструмента за запуск, ограничены контекст и результат. Отдельных лимитов CPU/RSS в приложении нет.

## Audit Log

PostgreSQL хранит инициатора, tenant, agent, задачу, исполнение, approval, время, действие, результат и ограниченный код ошибки. Запись намерения предшествует инструменту, успешный outcome обязателен для сохранения результата. У роли приложения нет UPDATE/DELETE для журнала. Фильтры API доступны по агенту, задаче, действию и началу периода. Журнал не содержит credentials и произвольных backend error strings. Для текущих сценариев объект изменений — задача и связанный approval. Универсальный журнал before/after внешних доменных изменений отсутствует.

## Human Approval и интерфейс

Marketing draft ожидает решения владельца. Approval связан с tenant, task, agent и хешем фиксированных параметров. Отказ завершает задачу, одобрение ставит её в очередь, истечение обрабатывается worker. Повторное решение и изменившийся хеш отвергаются. Approval проверяется при claim и повторно под lease перед записью инструмента и завершением. Черновик становится единственным долговременным результатом успешной попытки. Платёж, рассылка и публикация не представлены в наборе инструментов.

AI Settings содержит раздел «Требуют подтверждения», детали, срок, подтверждение и отклонение. BFF использует текущие tenant routing, session и CSRF. Запрос отправляет исходный хеш и блокирует повторное нажатие. Выполнены тесты Next.js UI с синтетическим API и отдельно тесты Go API с PostgreSQL.

## Agent Registry, Orchestrator, permissions и инструменты

Worker загружает семь существующих определений и выбирает разрешённое действие через Orchestrator. Задача получает allowlist из одного инструмента. Пользовательский payload не задаёт разрешения, tenant, worker proof или lease. Agent lease разрешает чтение только указанного варианта и связанной карточки после проверки активного диалога и полномочий владельца. Существующий Runner выполняет чтение цены. Финансы и аналитика получают агрегаты завершённых заказов, созданных за последние 30 дней. Сумма заказов не выдаётся за сверенную выручку или движение денег.

| Агент | Подключённый сценарий | Осталось |
| --- | --- | --- |
| Customer | Цена опубликованного варианта в контексте диалога | Квалификация, история и подготовка ответа через новые задачи |
| Sales | Цена варианта через каталог | Рекомендации услуг, подготовка заявки, сопровождение |
| Product & Inventory | Цена варианта через каталог | Анализ дефицита, спроса, рекомендации пополнения |
| Marketing | Внутренний черновик после явного решения владельца | Сегментация и метрики эффективности |
| Finance | Только чтение количества и суммы завершённых заказов | Расходы и бухгалтерские источники |
| Analytics | Те же достоверные агрегаты по tenant | Тренды, отчёты по нескольким источникам |
| Business Manager | План и сбор сохранённых результатов ограниченного процесса | Свободная декомпозиция и произвольные цепочки |

## Parent/child collaboration

Действие `coordinate` атомарно создаёт родительский запрос, Analytics read и Marketing draft. Только родитель создаёт одно поколение из двух фиксированных дочерних задач. Внутренние действия не расходуют provider budget. Все задачи проходят один Orchestrator, наследуют deadline и correlation. Родитель ожидает терминального состояния дочерних задач и сохраняет их результаты и отказы. Истечение родительского deadline завершает его без новых действий. Нет произвольных рекурсивных делегирований.

## Shared Business Context

Агент получает узкий scope из долговременно сохранённой задачи и проверенного lease. Legacy Business Type читается из проверенной PostgreSQL организации, приложению доступен текущий electronics профиль. Полная универсальная модель, услуги, бизнес-политики и customer context остаются на уровне существующих контрактов и валидаторов. Runtime автосервиса, строительства, автозапчастей, недвижимости, сервисных и гибридных компаний пока не подтверждён.

## Migrations и файлы

Добавлена `00018_agent_runtime.sql`. Предыдущие migrations сохранены. Migration 00018 Down допускает чистую схему и отказывается удалять накопленные агентные задачи. Новые таблицы используют составные tenant FK и FORCE RLS. Чтение канальных jobs прежним способом не раскрывает agent lease.

Backend изменён в `internal/agentruntime`, `internal/http/{agents,identity}.go`, `internal/catalog/service.go`, `internal/agent/tools.go`, `internal/platform/db/db.go` и `cmd/worker/main.go`. Тесты добавлены в существующий безопасный integration harness. Frontend изменён в `AgentApprovals.tsx`, `AISettings.tsx`, `premium.css`, BFF allowlist и Playwright spec.

Прямые tenant endpoints поддерживают POST/GET `agent-tasks`, GET `agent-audit`, GET `agent-approvals` и POST `agent-approvals/{approval}/decision`. В браузере подключён approval workflow.

## PostgreSQL, security и runtime tests

Финальный PostgreSQL harness завершился с exit 0. Проверены миграции, все 51 таблица с FORCE RLS, межtenantные SELECT/INSERT/UPDATE/DELETE, семь агентских сценариев, два и более параллельных worker attempts, повторная отправка идентичной задачи, восстановление lease, отсутствие успешного завершения без audit outcome, CSRF, истечение approval, неверный hash и повторное решение. Отдельный собранный worker-процесс выполнил вторую попытку после смоделированного прерывания первой, сохранил результат и завершился по SIGTERM. Регрессии прежних каналов прошли на синтетическом транспорте.

Начальные FAIL сохранены. Прежняя проверка populated rollback запускалась до появления строк агента. Тест теперь создаёт реальные задачи перед проверкой сохранности данных. До оптимизации inventory RLS запрос без агентского контекста превысил прежний лимит в одну секунду. Политика теперь проверяет наличие agent lease перед вызовом функции; лимит не увеличен.
