# Stage 2.6.2 Final Delivery — уведомления клиента Auto Service

## Baseline

Подтверждение сотрудником, резервы товара и времени и сохранение фактического результата Business Manager в Tasks API проверены на предыдущем этапе. См. [отчёт Closure](STAGE_2_6_2_CLOSURE_REPORT.md) и [исторические доказательства](../.local/stage-2-6-2-closure/INDEX.md).

## Реализация

Сотрудник может подготовить заявку по завершённому делегированию Auto Service в диалоге Telegram, WhatsApp или Instagram. Order API сверяет tenant, диалог, срок задачи, тип и точные параметры сохранённого предложения. Подтверждение и резервы проходят через существующий Order API. В событии заказа зафиксирован результат уже подтверждённой операции.

После выполнения дочерней задачи Business Manager миграция `00027` сохраняет сообщение в том же диалоге и использует существующие Telegram и WhatsApp outbox. ID задачи результата используется как ключ идемпотентности. Сообщение включает актуальный статус, услугу, время в часовом поясе организации, специалиста и детали, если они есть в результате. Суммы берутся из подтверждённых данных заказа. Статус бронирования и состояние резерва исходят из backend. При подтверждении сообщение объясняет, как обратиться за изменением или отменой.

Для тестового tenant требуются действующее подключение, проверенная привязка получателя к диалогу, режим `mock` и явное согласие клиента. Команды `booking_updates:on` и `booking_updates:off` принимаются как сообщения проверенного клиента через входящий канал. Последняя команда определяет состояние согласия в этом диалоге. Команды сохраняются в истории без вызова модели. Окно WhatsApp и текущие ограничения каналов действуют при постановке в очередь и отправке.

Перед вызовом транспортного адаптера worker снова сверяет диалог, получателя, согласие, версию и статус заказа и активность резерва. Изменения заказа и ограниченный по времени вызов транспортного адаптера сериализуются блокировкой заказа. Отмена, уже зафиксированная в PostgreSQL, блокирует ожидающее подтверждение. Расписание обрабатывается по текущим данным. Существующие состояния outbox сохраняют окончательные, временные и неопределённые исходы, а повтор для неопределённого исхода определяется существующим движком канала. Владелец может запросить причины недоступности и переходы доставки в `GET /api/v1/organizations/{id}/agent-audit` с фильтром `action=booking.delivery` или `action=booking.delivery_state`.

Instagram допускает формирование результата и его просмотр в Tasks API. В `00017_instagram_durable.sql` действует ограничение `sending_enabled=false`, а `instagram.Service.SendOne` возвращает отсутствие работы. Отдельный автономный `OfflineTransport` предназначен для контрактного тестирования и не подключён к существующему durable dispatch. Для Auto Service причина отказа сохраняется как `instagram_send_disabled`.
